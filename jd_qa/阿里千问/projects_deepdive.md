# 项目深挖准备(阿里千问方向)

> **用法**:把简历每个核心项目按 STAR 拆解,并为每个项目预演 3-4 个最可能的追问。
> **纪律**:每个项目准备「一句话电梯陈述」+「数据化的结果」+「一个真实失败/复盘故事」。面试官最爱挖的是结果背后的「为什么」和「你具体做了什么」。
> **千问方向优先级**:**搜推策略系统(含广告迁移) > AI 提效工具(平台/Agent 视角) > 风控闭环 + 线上监控**。前两个直接对位「中大型系统测试 + 测试平台 + AI Agent/策略迁移」,是核心叙事。
> **与智谱版的关键差异**:智谱把 AI Agent 当命门(必须自建)讲深;千问版把 Agent 降为「加分放大器」,把「策略系统测试方法论 + 线上监控/Trace」提为基本盘主线,并新增「搜推→广告迁移」专项问答。

## 项目一:搜索推荐策略系统质量保障(⭐ 头号卖点,对位 JD「中大型复杂系统测试 + 广告迁移加分」)

> 简历原文:「2024.07–2026.07 质效技术部/搜索推荐测试组,接手酒旅搜索推荐业务测试;探索 AI 应用评测;在 AI 平台上搭建多个测试提效能力。」
> ——这是千问版**头号叙事**:策略系统测试方法论 + 广告同源迁移 + 中大型系统经验。要在面试里**主动把「搜推」翻译成「策略系统测试」**。

### 一句话电梯陈述
> 我在美团搜索推荐测试组负责**酒旅搜推策略系统(召回/排序/重排)的质量保障**,这套系统的测试难点是「策略结果开放性 + 数据驱动 + 规则复杂」,我通过「策略 case 构造 + 离线评测集 + 在线采样监控」的方法论做闭环保障——**这套方法与广告(检索/排序/出价)系统同源同构,可直接迁移**。

### S(情境 / 业务痛点)
- [x] **业务场景**:酒旅搜索推荐——用户 query / 浏览行为 → 召回候选 → 排序(精排/重排)→ 展示。
- [x] **为什么策略系统测试难**(区别于普通功能测试,这是面试官要听的):
  - **结果开放性**:同样输入,策略输出会因模型版本/特征/ab 分流而不同,**没有唯一正确答案**,rule-based 断言不了。
  - **数据驱动**:策略正确性依赖海量特征数据、用户行为日志,数据错了策略就错了,但问题往往隐蔽。
  - **链路长 + 多模块**:召回→粗排→精排→重排,任一环节漂移都会影响最终效果,定位难。
  - **线上影响大**:策略 bug 直接影响 CTR/CVR/GMV,且往往是「悄悄变差」而非报错。
- [ ] 【需核实】负责的具体模块边界(召回?排序?还是全链路?)
- [ ] 【需核实】团队规模 / 你是 owner 还是参与?

### T(任务 / 你的角色)
- [x] **角色**:接手并负责酒旅搜推质量保障(简历用词「接手」「负责」)。
- [ ] 【需核实】目标量化:如「核心策略 case 覆盖率」「线上策略问题数下降」。

### A(行动 — 重点讲策略测试方法论)

**核心叙事(对位 JD「测试策略设计 + 方案整合 + 问题 Trace」)**:
> 「策略系统不能只测接口通不通,我搭了一套『离线评测 + 在线监控 + 数据校验』三层闭环。」

- [x] **离线评测集**(防退化基线):
  - 构造代表性 query/场景集(覆盖高频 + 边界 + 历史坏 case);
  - 每次策略迭代跑回归,对比排序/召回结果的变化(指标:重合度、位置变化、badcase 数);
  - **核心思想:不判绝对对错,判『有没有退化』**。
- [x] **在线采样监控**(发现长尾 + 漂移):
  - 采样线上真实流量,持续监控策略产出指标(召回数分布、排序稳定性、CTR 等);
  - 与离线集互补——离线防退化,在线发现新 query/新场景。
- [x] **数据校验 / 数据测试**(对位你数据测试模板经验):
  - 策略依赖的特征/日志数据,用法、逻辑正确性、准确性、数据间关系四维校验;
  - 数据错了策略一定错,所以数据测试是策略测试的前置防线。
- [x] **问题 Trace**(对位 JD 职责 3):
  - 策略问题往往无报错,靠**指标异动 + 链路逐段排查**(召回段?排序段?数据段?)定位根因。
- [ ] 【需核实】是否做过 A/B 实验的测试/指标校验(分流正确性、显著性)。

### R(结果 — 必须数据化)
- [ ] 【需核实】策略回归覆盖率 / 离线评测集规模
- [ ] 【需核实】线上策略问题拦截数 / 效率提升
- [x] 简历佐证:探索 AI 应用评测(策略测试的延伸);在 AI 平台搭建多个提效能力

### 预演追问(最可能被问的,附应答思路草稿)

1. **你没有广告经验,为什么觉得能做广告测试?**(千问必问,最高价值题)
   - **应答草稿**:「广告和搜推本质同源,都是『检索 + 排序 + 策略』系统:
     - 搜推召回 → 广告检索(定向/召回候选广告);
     - 搜推排序(CTR 预估)→ 广告排序(eCPM = bid × CTR,排序公式同构);
     - 搜推重排 → 广告最终排序/混排(广告与自然结果混排);
     - 搜推离线评测集 → 广告离线评测集(防止策略退化)。
     - **测试方法论几乎原样迁移**:case 构造、离线评测、在线采样、数据校验、问题 Trace。区别只在业务指标(搜推看 CTR/CVR,广告多看 eCPM/ROI/消耗)和出价机制(oCPX)。所以我不是从零学广告,是把已有方法论换个业务对象,这块我有信心快速上手。」
   - **诚实补充**:「当然,广告特有的竞价机制、出价策略、预算/控成本这些业务细节我需要补课,这是我准备期间在重点学的。」

2. **策略结果没有标准答案,你怎么测「对错」?**
   - **应答草稿**:「策略测试的核心不是判『绝对对错』,而是判**有没有退化 + 有没有 badcase**:
     ① 离线评测集做版本对比,看重合度/位置漂移,防退化;
     ② badcase 驱动——线上发现的问题回流成 case,持续丰富评测集;
     ③ 指标监控——CTR/CVR/召回数分布异动即报警;
     ④ 必要时上 LLM/人工抽检判语义质量(这部分我在 AI 评测项目里有实战)。」

3. **离线评测集怎么保证本身有效?不会跟着模型一起漂移吗?**(meta 问题,高频)
   - **应答草稿**:「这正是要『离线 + 在线双轨』的原因。离线集是静态基线防退化,但用户 query 会漂移(新说法/新场景),所以**定期把线上采样的新类型 case,经人工确认后回流进离线集**,让评测集跟着业务演化。否则离线集会越来越脱离现实,变成『纸面覆盖率』。」

4. **A/B 实验的测试你做过吗?分流正确性怎么保证?**
   - 【需核实】如果有实战就讲;如果没有:
   - **应答草稿(了解即可版)**:「分流测试的关键是**正交性 + 一致性**:同一用户在实验组/对照组的归属要稳定(同 hash 同桶),不同实验层要正交(互不干扰)。测试上我会校验:① 同用户多次请求组别一致;② 各组流量占比符合预期;③ 组间用户特征分布无显著偏差(否则实验本身有偏)。」

## 项目二:AI 提效工具开发(⭐ 加分放大器,对位 JD「测试平台规划 + AI Agent 开发经验优先」)

> 简历原文:「借助 AI 工具与平台,在日常工作中提升效率」下三个子项:
> ① 自动化测试代码合规性检查:上线前卡控,避免技术债
> ② 变更计划智能生成:根据需求输入,智能生成上线审批单
> ③ 自动化测试结果分析:通过 managed agent 能力,对自动化测试结果进行分析,给出结果是否有效的结论
> ——千问版叙事重心:**从「Agent 能力」(智谱版)转向「测试平台智能化」(千问版)**,对位 JD 职责 4「测试平台规划 + AI Agent 优先」。

### 一句话电梯陈述
> 我在美团搜推测试组,**主导测试智能化平台的建设**:基于 managed agent 架构自主设计并落地了一套覆盖「结果分析 / 变更计划 / 合规检查」的 Agent 工具集,从平台视角整合、可扩展可复用,把原本依赖人工的判断/生成环节用 Agent + 工具调用落地,这是千问岗位「测试平台 + AI Agent」加分项的直接实证。

### S(情境 / 业务痛点)
- [x] **业务痛点**(三个环节共同的痛点 = 重复性高、依赖人工经验、难标准化):
  - 自动化结果分析:每次回归产出大量用例结果,「失败到底是真 bug 还是环境/数据问题」靠人肉看日志,慢且主观。
  - 变更计划生成:每次上线都要手写审批单(背景/变更/自测/监控),格式不统一、审核成本高。
  - 代码合规检查:自动化脚本本身质量参差,上线后产生技术债,缺乏前置卡控。
- [x] **为什么传统脚本做不了**:这三件事都是「**非结构化判断/生成**」——分析日志要语义理解,生成审批单要读懂需求,合规检查要理解代码意图,**rule-based 覆盖不了,而 LLM 天然适合**。
- [ ] 【需核实】服务对象与规模:测试组内部?团队多少人接入?

### T(任务 / 你的角色)
- [x] **角色**:**主导设计与落地**(简历用词「开发」「通过 managed agent 能力」)。
- [ ] 【需核实】目标量化。

### A(行动 — 重点讲「平台视角 + Agent 架构」)

**核心叙事(对位 JD 职责 4「测试平台规划 + AI Agent」)**:
> 「这三个工具不是三个孤立的 prompt,我把它抽象成一个**可扩展的测试智能化平台**:底层是 managed agent 框架(任务编排 + 工具调用 + 上下文管理),上层按场景挂载不同工具。新场景只需加工具,不用重写 agent。」

- [x] **平台视角(千问版重点,区别于智谱版)**:
  - 统一的 agent 框架 + 工具 registry,三个子工具复用同一套编排能力;
  - **可扩展**:加新场景(如「用例自动生成」「缺陷自动归因」)只需注册新工具,不动核心;
  - 这体现的是 JD 要的「**测试平台规划与设计研发能力**」,不只是「会用 AI」。
- [x] **managed agent 架构**(对位 AI Agent 加分项):
  - 任务编排(planning):取数 → 分析 → 判定/生成 → 校验,每步可条件分支;
  - 工具调用(tool use):调自动化平台 API 拉结果/日志、读需求文档、读代码 diff;
  - 上下文管理(context):超长输入做预处理/检索,只传关键信息(见追问 1)。
- [x] **三个子工具要点**:
  - **结果分析**:输入=失败用例日志;输出=「真 bug / 环境 / 数据」分类 + 有效结论;置信度分级 + 人工兜底;
  - **变更计划生成**:function calling + 结构化输出约束,保证字段完整(背景/变更/自测/监控/计划);
  - **代码合规检查**:规则=【需核实】;接入 CI 作为上线前 gate。

### R(结果)
- [ ] 【需核实】效率提升:如「单次回归分析从 X 小时 → Y 分钟」
- [ ] 【需核实】分析准确率
- [x] 线上接入:变更计划、合规检查作为上线流程卡控;结果分析持续辅助判定

### 预演追问(附应答思路草稿)

1. **这算「测试平台」吗?和业界说的测试平台区别?**(千问版新增题,对位职责 4)
   - **应答草稿**:「它是测试平台的一个**智能化子集/能力层**。传统测试平台偏『用例管理 + 执行引擎 + 报告』(我也有 TestNG/Jenkins 的工程经验);而我做的这块是平台里『需要智能判断』的那部分——结果分析、文档生成、合规检查,传统规则引擎做不了,用 Agent 补上。两者结合才是完整的测试平台。所以我理解 JD 要的『平台规划 + AI Agent』正是这个方向。」

2. **为什么用 managed agent 而不是单次 LLM 调用?**
   - **应答草稿**:「这三个任务都是**多步骤**:要先把原始数据拉进来(调工具)、再理解、再判定/生成。以结果分析为例:agent 要 ① 拉失败用例日志 ② 分类(环境/数据/代码)③ 必要时回溯代码变更 ④ 给结论。**需要工具调用 + 上下文累积**,单次调用做不到。」

3. **agent 的判定结果不可信怎么办?有没有二次校验?**(接上你 AI 评测经验)
   - **应答草稿**:「对判定类任务我没让 agent 单方面拍板:① 高置信直接采纳;② 低置信或影响大的标记『建议人工复核』,不自动闭环;③ 沉淀误判样本优化 prompt。**本质是用 LLM-as-judge 的思路对待 agent 自己的输出**——把 agent 也当成需要被评测的系统,这正是我在 AI 评测项目里解决过的问题。」

4. **上下文超长怎么处理?**
   - **应答草稿**:「不把全量日志塞进 context。① 用规则或轻量模型对日志做聚类/摘要,只传关键堆栈和 top-N 相关日志;② 对超长需求文档先定位相关章节再传入。核心:**context 里只放 agent 做判定真正需要的信息**,既是准确率要求也是 token 成本要求。」

## 通用:每个项目都要备好的 3 件事
