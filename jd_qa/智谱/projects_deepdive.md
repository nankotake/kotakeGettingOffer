# 项目深挖准备(Day 1 产出)

> **用法**:把简历每个核心项目按 STAR 拆解,并为每个项目预演 3-4 个最可能的追问。
> **纪律**:每个项目准备「一句话电梯陈述」+「数据化的结果」+「一个真实失败/复盘故事」。面试官最爱挖的是结果背后的「为什么」和「你具体做了什么」。
> **优先级**:**AI 提效工具 > AI 评测 > 风控闭环**。前两个是你区别于其他候选人的核心叙事。

## 项目一:AI 提效工具开发(⭐ 头号卖点,对位 JD「自建 AI 测试 Agent」)

> 简历原文:「借助 AI 工具与平台,在日常工作中提升效率」下三个子项:
> ① 自动化测试代码合规性检查:上线前卡控,避免技术债
> ② 变更计划智能生成:根据需求输入,智能生成上线审批单(背景/变更内容/自测结果/监控方式/变更计划)
> ③ 自动化测试结果分析:通过 managed agent 能力,对自动化测试结果进行分析,给出结果是否有效的结论
> ——简历里写得很低调,面试时要**主动升格为「Agent 架构能力」叙事**。

### 一句话电梯陈述
> 我在美团搜索推荐测试组,基于公司 AI 平台 **自主设计和落地了一套 managed agent 测试智能化工具**,覆盖自动化结果分析、变更计划智能生成、自动化代码合规检查三个高频测试环节,把原本依赖人工判断/编写的环节用 **Agent 编排 + 工具调用** 落地,显著提升了团队日常效率。

### S(情境 / 业务痛点)
- [x] **业务痛点**(三个环节共同的痛点 = 重复性高、依赖人工经验、难标准化):
  - 自动化结果分析:每次回归产出大量用例结果,「失败到底是真 bug 还是环境/数据问题」靠人肉看日志,慢且主观。
  - 变更计划生成:每次上线都要 RD 手写审批单(背景/变更/自测/监控),格式不统一、审核成本高。
  - 代码合规检查:自动化脚本本身质量参差,上线后产生技术债,缺乏前置卡控。
- [x] **为什么传统脚本做不了**:这三件事都是「**非结构化判断/生成**」——分析日志要语义理解,生成审批单要读懂需求文档,合规检查要理解代码意图,**rule-based 脚本覆盖不了,而 LLM 天然适合**。
- [ ] 【需核实】服务对象与规模:给测试组内部用?团队约多少人接入?
- [ ] 【需核实】量化瓶颈:如「每次回归分析人工耗时约 X 小时」「每周 Y 份审批单」。

### T(任务 / 你的角色)
- [x] **角色**:**主导设计与落地**(简历用词「开发」「通过 managed agent 能力」),非被动参与。
- [ ] 【需核实】目标量化:如「三个工具全部上线接入」「分析准确率 ≥ X%」。

### A(行动 / 技术方案 — 重点讲 Agent 架构)

**核心叙事(对位 JD 第 3 条:任务编排/工具调用/上下文管理)**:
> 「这三个工具看似独立,底层我抽象成了一个 **managed agent 框架**:agent 负责任务编排,按需调用不同工具(拉取自动化结果、读取需求/代码、输出结构化结论),并管理跨步骤的上下文。所以它不是三个孤立的 prompt,而是一个可扩展的测试 Agent 体系。」

- [x] **为什么用 managed agent 而不是单次 LLM 调用?**(必答,体现你懂编排)
  - 单次调用只能做「输入→输出」一步;而这三个任务都是**多步骤**:要先把原始数据拉进来(调工具)、再理解、再判定/生成。
  - 以「自动化结果分析」为例:agent 要 ① 拉取失败用例及日志 ② 分类(环境/数据/代码)③ 必要时回溯代码变更 ④ 给出「是否有效 bug」结论。**需要工具调用 + 上下文累积**,所以用 managed agent。
- [x] **任务编排(planning)**:agent 接到任务后,按「取数 → 分析 → 判定/生成 → 校验」编排,每步可条件分支(如分析阶段发现信息不足,再调工具补充)。
- [x] **工具调用(tool use)**:
  - 调自动化平台 API 拉取用例执行结果与日志
  - 读取需求文档 / 代码 diff(变更计划、合规检查)
  - 读取历史知识库辅助判定
- [x] **上下文管理(context)**:见下方追问 1(超长处理)。
- [x] **三个子工具的实现要点**:
  - **自动化结果分析**:输入=失败用例日志;输出=「真 bug / 环境问题 / 数据问题」分类 + 有效结论。判定依据=错误日志语义 + 代码变更关联。误判治理见追问 3。
  - **变更计划智能生成**:输入=需求文档 + 变更范围;输出=结构化上线审批单。靠 **function calling / 结构化输出约束** 保证字段完整(背景/变更内容/自测结果/监控方式/变更计划)。
  - **代码合规检查**:规则=【需核实:如断言规范、资源释放、硬编码等】;卡控=**接入 CI,作为上线前 gate**,不合规阻断。
- [ ] 【需核实】底层平台/模型:公司 AI 平台名称?用的哪家大模型(GLM?内部模型?)

### R(结果 — 必须数据化)
- [ ] 【需核实】效率提升:如「单次回归分析从 X 小时 → Y 分钟」「审批单编写时间节省 Z%」
- [ ] 【需核实】分析准确率/有效性判定准确率
- [x] 线上接入情况(简历佐证):变更计划、合规检查已作为上线流程卡控;结果分析持续辅助判定
- [ ] 【需核实】一个真实的误判/踩坑案例(见追问)

### 预演追问(最可能被问的,附应答思路草稿)

1. **上下文超长怎么处理?**
   - **应答草稿**:「日志类输入容易超长。我的做法是**不把全量日志塞进 context**,而是先做一次预处理/检索:① 用规则或轻量模型对日志做聚类/摘要,只把关键堆栈和 top-N 相关日志传给 agent;② 对超长需求文档,先定位与本次变更相关的章节再传入。核心思想是 **context 里只放 agent 做判定真正需要的信息**,而不是图省事全量灌进去——这也是 token 成本和准确率的双重要求。」

2. **工具调用失败时如何重试/降级?**
   - **应答草稿**:「我做了分层处理:① 网络类瞬时失败→指数退避重试(2~3 次);② 工具持续失败→**降级**:分析类任务降级为『标记为需人工确认』而不是硬给结论,避免误导;生成类任务降级为模板兜底;③ 所有失败都记录,便于复盘工具稳定性。原则是 **关键路径不静默吞错,宁可让人介入**。」

3. **agent 的判定结果本身不可信怎么办?有没有二次校验?**(这题最关键,接上你 AI 评测经验)
   - **应答草稿**:「这正是我在另一个项目(AI 评测)里重点解决的问题。对结果分析这类判定,我没有让 agent 单方面拍板:① 高置信结论直接采纳;② 低置信或影响大的结论,**标记为『建议人工复核』**,不自动闭环;③ 同时沉淀误判样本持续优化 prompt 和判定规则。**本质上是用 LLM-as-judge 的思路对待 agent 自己的输出**——把 agent 也当成一个需要被评测的系统。」

4. **如果让你重做,会怎么改进?**(复盘,体现成长)
   - **应答草稿**:「三个方向:① **评测体系前置**——当时对 agent 输出质量的度量偏经验,如果重做我会先建一个标注评测集,用数据驱动 prompt/工具迭代(现在我在 AI 评测项目里就是这么做的);② **工具调用更解耦**——早期工具耦合较紧,可改成更标准的 tool registry,便于复用和单测;③ **成本可观测**——加上 token 消耗埋点,按场景做模型分级(简单判定用小模型,复杂分析用大模型)。」

5. 【备用】**三个工具里最难的是哪个?为什么?**
   - **应答草稿**:「自动化结果分析。因为前两个本质是『结构化生成』,约束明确;而结果分析是**开放性判定**,要区分『真 bug / 环境 / 数据』,误判代价高。所以我在这块花最多精力做置信度分级和人工兜底。」

## 项目二:酒店办事出游场景 AI 评测(⭐ 对位 JD「AI Agent/LLM 应用测试」加分项)

> 简历原文:「住宿列表页为更好承接办事、出游场景需求,接入找一找、比一比能力。负责系统功能测试、AI 产出评测。通过 LLM-as-a-judge 的方式,实现 AI 项目的离线、在线评测能力,涉及严谨性、安全性、一致性等指标的评测。评测准确率 90% 左右,总计发现 4 类有效问题(绝对化表述、亲子场景识别、时间段识别、字数卡控失效)。」
> ——这个项目和智谱的「LLM 应用质量保障」加分项**几乎逐字对应**,要讲透方法论,尤其是「如何迁移到 Coding Agent」。

### 一句话电梯陈述
> 在酒店列表页接入「找一找/比一比」AI 能力后,我用 **LLM-as-a-judge** 搭建了覆盖严谨性/安全性/一致性的离线+在线评测体系,评测准确率约 90%,从中发现并推动修复了 4 类有效问题(绝对化表述、亲子场景识别、时间段识别、字数卡控失效)。

### S(情境)
- [x] **业务场景**:住宿列表页接入「找一找/比一比」——用户用自然语言/模糊意图找酒店,AI 生成推荐话术与结果。
- [x] **为什么需要 AI 评测**(传统功能测试覆盖不了什么):
  - 传统功能测试能验证「接口通不通、结果对不对」,**但 AI 生成的自然语言回答是开放性的**——话术是否绝对化(合规风险)、场景识别是否正确(亲子/办事/出游)、是否违反字数/时段约束,这些**没有标准答案,rule-based 断言不了**,必须用语义级评测。
  - 一句话:**传统测『对错』,AI 评测测『好不好、合不合规、稳不稳定』**。

### T(任务)
- [x] **职责**:系统功能测试 + AI 产出评测(**评测体系是我搭建的**,这是亮点)。

### A(行动 — 重点讲评测方法论)

**核心叙事**:「我用 LLM-as-a-judge 做语义级评测,关键是解决『评判者本身可不可信』这个 meta 问题。」

- [x] **LLM-as-judge 的 prompt 怎么设计?**
  - **结构**:角色设定(你是酒旅质量评测员)+ 评测维度定义(严谨性/安全性/一致性)+ 评分标准(每个维度 rubric)+ few-shot(正反例)+ **输出格式约束**(结构化 JSON,含维度分数 + 判定理由)。
  - **关键**:判**理由**比判**分数**更重要——要求 judge 给出扣分依据,便于人工复核和可信度校验。
- [x] **怎么保证 judge 可信?(评判者偏差)**——这是面试官最爱挖的点:
  - ① **人工抽样校准**:定期抽样人工复核 judge 结论,统计一致率,不一致的进 badcase 库优化 prompt;
  - ② **rubric 明确化**:把『什么叫绝对化』『什么叫亲子场景』写成可操作的标准,减少 judge 主观空间;
  - ③ 【需核实】是否做多 judge 投票或与人工标注做一致性对齐(如 Cohen's Kappa)。
- [x] **三个指标怎么算**(给可讲清的定义,具体阈值【需核实】):
  - **严谨性**:话术是否有绝对化/夸大/违规表述(如「最便宜」「保证」)→ 合规红线。
  - **安全性**:是否泄露隐私、诱导、超出业务边界、有风险引导。
  - **一致性**:相同/相似输入下,AI 输出是否稳定(语义一致,而非字面一致)。
- [x] **离线 vs 在线评测**:
  - **离线**:固定评测集(标注好的 case 集),版本迭代时跑回归,看指标是否退化——**保证不越改越差**。
  - **在线**:采样线上真实流量,持续监控 AI 产出质量——**发现长尾和漂移**。
- [ ] 【需核实】评测集规模与标注方式(多少条?人工标注还是规则辅助?)

### R(结果)
- [x] **准确率 90%**——面试时**主动澄清口径**(见追问 1),别让面试官以为是含糊数字。
- [x] **4 类有效问题**(每类准备好「具体 case + 为什么是问题 + 怎么发现的」):
  - **绝对化表述**:如 AI 生成「这家是附近最便宜的酒店」→ 违反广告法合规。传统测试抓不到(没有确定输入输出),靠 judge 语义识别。
  - **亲子场景识别**:用户带娃出行,AI 没识别亲子意图,推荐了不适合带孩子的酒店 → 场景理解错误。
  - **时间段识别**:【需核实具体 case,如「当天预订」识别成「未来日期」,或营业时段理解错】
  - **字数卡控失效**:AI 回复超出约定字数上限,说明长度约束没生效 → 提示词/后处理约束漏洞。
- [x] **闭环**:发现 → 提工单/推动修复 → 修复后用离线评测集回归确认不退化 → 进在线监控。

### 预演追问(附应答思路草稿)

1. **90% 准确率怎么来的?剩下的 10% 是什么错判?**(必问,数字口径一定要清)
   - **应答草稿**:「90% 指 **judge 判定与人工标注的一致率**(【需核实是否准确】)。剩余 10% 主要两类:① judge 对边界模糊 case(如轻度夸张算不算绝对化)判定不稳;② 新出现的、评测集没覆盖的表述形态。我的处理是把这些不一致全部进 badcase 库,定期回流优化 rubric 和 few-shot,逐步收敛。**所以 90% 不是终点,是持续迭代的基线。**」

2. **LLM-as-judge 比 rule-based / 人工好在哪?劣势在哪?**
   - **应答草稿**:
     - **优势**:rule-based 抓不到语义(「最划算」「性价比之王」都是绝对化但字面不同);人工不可扩展、成本高、主观。judge 能做语义级、可批量、可标准化。
     - **劣势**:① 本身有偏差,需要校准;② 成本(token);③ 对未见过的 case 泛化不稳。**所以我的策略是 judge 为主 + rule 兜底关键红线 + 人工抽检**,三者结合而不是单一依赖。

3. **如何迁移到 Coding Agent 的评测?**(智谱一定会问,最高价值题)
   - **应答草稿**:「完全可迁移,三个维度一一对应:
     - 严谨性 → **代码正确性**:生成的代码是否真能跑、是否符合需求语义(类似我判话术合规)。
     - 安全性 → **不引入漏洞/不越权**:代码是否有注入、越权、危险操作(类似我判话术安全)。
     - 一致性 → **相同输入输出稳定**:同一 prompt 多次生成是否行为一致、diff 是否可控。
     - 方法论也一样:LLM-as-judge 做语义判定 + 离线评测集防退化 + 在线采样监控长尾。**区别只是评测对象从『自然语言话术』换成『代码/diff/工具调用』,判定 rubric 要重写,但评测框架可直接复用。**」

4. **评测集的数据漂移问题怎么处理?**
   - **应答草稿**:「这正是要『离线 + 在线双轨』的原因。离线集是静态基线,防退化;但用户真实 query 会漂移(新说法、新场景),所以**定期把线上采样到的新类型 case,经人工确认后回流进离线集**,让评测集跟着业务演化。否则离线集会越来越脱离现实,90% 也会变成『纸面准确率』。」

5. 【备用】**如果 judge 和人工判定冲突,信谁的?**
   - **应答草稿**:「默认信人工,但**不轻易推翻 judge**——先分析冲突原因:是 rubric 不清晰?case 本身就是边界?还是 judge 真错了?分类处理。系统性冲突→改 rubric;偶发冲突→记入已知盲区。目的是让评测体系越用越准,而不是每次都临时拍板。」

## 通用:每个项目都要备好的 3 件事

- [ ] **一句话电梯陈述**(面试官问"讲讲这个项目"时第一时间抛出)
- [ ] **一个数据化的结果**(没有数据的项目没有说服力)
